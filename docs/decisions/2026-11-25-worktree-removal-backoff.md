# 2026-11-25: worktree removal backs off

A failed removal of a task worktree is retried after 1, 2, 4, 8 ... minutes, at most an hour (`core/src/removal.rs`), with the failure count, time and error stored on the `worktrees` row (migration 0023); after 6 failures nothing is retried until the user answers the keep-or-delete ask, which now opens only then and names the path and the last error. A folder git does not know as a worktree is ended as a stray folder at once, and a close that is still backing off skips the lifecycle transition, so "worktree neither removed nor kept" is no longer refused on every pass. The live store showed 209 `worktree-refused` events and 205 such refusals from the tick retrying the same removal on every pass, against a Windows file lock or a script that could never succeed.
