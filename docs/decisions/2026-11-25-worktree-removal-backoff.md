# 2026-11-25: worktree removal backs off

A removal that failed for a transient reason (a file held open, `Permission denied`, a git lock, or an OS error code such as 5, 16, 32 or 145; `classify`) is retried after 1, 2, 4, 8 and 16 minutes (`core/src/removal.rs`), with the failure count, time and error stored on the `worktrees` row (migration 0023); any other refusal, such as a tree that still holds work, asks the user at once, since retrying cannot change it; after the sixth transient failure (about 31 minutes in all) nothing is retried until the user answers the keep-or-delete ask, which names the path and the last error; the answer clears the counts, and a failed Delete raises one more ask that says delete was tried. `close --force` and a user-run `headwork clean` ignore the backoff. A folder git does not know as a worktree is ended as a stray folder at once, and a close that is still backing off skips the lifecycle transition, so "worktree neither removed nor kept" is no longer refused on every pass. The live store showed 209 `worktree-refused` events and 205 such refusals from the tick retrying the same removal on every pass, against a Windows file lock or a script that could never succeed.
